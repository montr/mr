## 7. Risks, Constraints, and Deviation Policy

54. Monaco and docx-preview are browser-heavy and jsdom cannot validate their visual rendering. Keep adapters narrow, automate application-owned lifecycle and state, and require actual-browser verification for rendering, focus, layout, and downloads.
55. Preview operations and HTTP requests can settle after template or JSON replacement. Revision tokens, cleanup, and stale-completion tests are required so obsolete work cannot repaint the UI or restore invalidated results.
56. Ant Design and Monaco can materially increase bundle size. This developer playground has no approved bundle-size target; use direct imports and production mode, record resulting artifact sizes, and do not introduce a different component/editor stack without PO-approved scope change.
57. `Content-Disposition` parsing and browser downloads vary by platform. Accept only a safe terminal filename, remove path/control characters, fall back to `document.docx`, and verify both header and fallback behavior automatically plus one real browser download manually.
58. API Problem Details are singular today, while the specification also requires defensive support for validation-style collections. Normalize known safe shapes without inventing new server behavior; malformed or HTML responses become concise generic diagnostics rather than raw content.
59. The repository currently has no authoritative shared product-version source. Frontend package metadata will be the single Feature 004 source for the provisional `0.0.1` footer label and release URL. Introducing a cross-.NET/npm version pipeline would be outside this feature.
60. The existing sample template contains a `Materials` collection, so `{"Materials":{}}` is a concrete syntactically valid incompatibility expected to exercise `generation.invalid_data` and HTTP `422`. Confirm the actual live response rather than hardcoding it in UI tests or production code.
61. No deviations from the approved specification are proposed. If dependency compatibility, browser security, or actual API behavior requires a material change to technology, scope, contract, acceptance evidence, or workflow, stop and route the decision through the Orchestrator and Product Owner before implementation proceeds.

## 13. Follow-up Architect Investigation — 2026-10-14

72. This investigation is planning evidence only. It inspected the approved specification and plan, v10 mockup, implementation review and Product Owner manual findings, current frontend source and configuration, installed `docx-preview` 0.4.1 package source and documentation, and OOXML in `Samples/sample.template.docx` and `Samples/sample.docx`. No retained generated or browser-downloaded DOCX was present under `/private/tmp` at inspection time. No production, test, configuration, README, status, server, browser, controller, suite, build, or Git-index operation was performed.
73. The two DOCX preview failures have one confirmed cause. The template main document contains 21 paragraph-level `w:fldSimple` elements whose child runs contain visible cached labels such as `«Project.Name»`, `«Reference»`, and the collection markers. The retained generated sample contains 35 paragraph-level `w:fldSimple` elements whose child runs contain the populated scalar and repeated-table values. The generated OOXML therefore contains the values that Word displays; neither generation nor download erased them.
74. Installed `docx-preview` 0.4.1 does not preserve those elements. Its paragraph parser handles runs, hyperlinks, smart tags, bookmarks, comments, math, content controls, and changes, but has no paragraph-level `fldSimple` branch. Its only `fldSimple` parsing branch is inside run parsing, and the renderer has no `SimpleField` case. Consequently the library drops each sample field together with its cached child text before HTML rendering. This directly explains invisible template MERGEFIELD labels and blank generated scalar/table cells. CSS clipping, stale rendering, missing API values, and Word-only field recalculation are not supported causes for these samples.
75. The recommended correction is a narrow preview-only DOCX normalization boundary before `renderAsync`. Load a private copy of the selected or generated package, inspect only supported Word story XML parts, and replace each `w:fldSimple` wrapper with its existing child nodes. The cached runs and text then remain ordinary OOXML content that `docx-preview` already renders. Render the normalized copy, but retain the original template for multipart submission and retain the exact original API Blob for download. Do not evaluate MERGEFIELD instructions, generate values, alter Core/API behavior, mutate the source Blob, or expose XML as HTML.
76. The normalizer should cover `word/document.xml`, headers, footers, footnotes, and endnotes so preview behavior matches the stories already supported by MonoReport. It should use namespace-aware XML operations, fail the preview with the existing concise warning on malformed package/XML, preserve non-field content and run formatting, and participate in the existing detached-host and stale-render lifecycle. If it imports the package ZIP library directly, declare and lock it as a direct dependency rather than relying on `docx-preview`'s transitive dependency.
77. This approach is preferred over four alternatives. Post-render DOM insertion cannot recover nodes discarded during parsing and risks layout drift. The experimental `parseAsync`, internal model, and `h` hook cannot recover the ignored paragraph children and are explicitly unstable. Forking or patching `docx-preview` creates a broad vendor-maintenance and security burden. Changing Core output or downloaded bytes violates the approved boundary and could damage Word field semantics. Replacing the viewer or fabricating a separate HTML document would expand scope and reduce fidelity.
78. The main tradeoffs are bounded extra browser memory and ZIP/XML processing time, plus ownership of a small OOXML preview adapter. Fidelity improves because existing cached runs and formatting are preserved, but remains limited to cached field results and `docx-preview`'s general rendering capabilities. Security is stronger than HTML synthesis because field text continues through the library's text-node rendering; the implementation must still avoid `innerHTML`, external entity processing, and unbounded diagnostic disclosure. The original request/download bytes remain authoritative and unchanged.
79. Focused regression coverage should use a minimal DOCX fixture containing paragraph-level simple fields in ordinary paragraphs and table cells. It should prove template cached labels and generated cached values survive normalization, unrelated content is unchanged, malformed normalization becomes a preview warning, stale renders remain detached, generation receives the original File, and Download receives the original response Blob. A real-browser manual check should confirm the sample template labels and generated scalar and repeated-table values are visible, while the downloaded document remains byte-identical to the API response and opens with the same populated content.

### 14.1 Proposed Architecture and Dependency Boundary

87. Add `MonoReport.UI/src/services/docxPreviewNormalization.ts` as a DOCX-specific preview adapter. Its single responsibility is to accept a `Blob` or `File`, load a private ZIP copy, normalize supported WordprocessingML story parts, and return a new preview `Blob`. It must not mutate or replace the source object held by `App`, interpret field instructions, generate document values, call the API, or participate in download naming or bytes.
88. Add `jszip` 3.10.2 as a pinned direct production dependency in `MonoReport.UI/package.json` and regenerate `package-lock.json`. `docx-preview` already resolves that version transitively, but direct use requires direct declaration and lock ownership. Use browser-native `DOMParser` and `XMLSerializer` for namespace-aware XML operations rather than adding another XML framework. This is the smallest maintainable tooling choice and avoids relying on `docx-preview` internals or unstable hooks.
89. Normalize only `word/document.xml`, `word/header*.xml`, `word/footer*.xml`, `word/footnotes.xml`, and `word/endnotes.xml`. Discover the numbered header/footer parts from ZIP entries rather than assuming a fixed count. Ignore missing optional stories. Recognize both transitional and strict WordprocessingML namespace URIs, and select `fldSimple` by namespace and local name rather than by an assumed prefix.
90. For every supported `w:fldSimple`, move its existing child nodes into the wrapper's position in their original order, then remove only the wrapper. This preserves cached runs, text, styling, hyperlinks, and surrounding paragraph or table structure. All non-field XML, ZIP entries, relationships, and media remain unchanged in the private preview package. Serialize and replace only story parts that actually contain supported wrappers.
91. A malformed ZIP, malformed supported XML part, unavailable browser XML API, or ZIP reassembly failure must reject normalization and flow into the existing concise Template or Result preview warning. Diagnostics must not expose package XML or internal stack traces. A supported story with no `fldSimple` returns a valid preview copy without invented content. Empty or childless `fldSimple` behavior remains a Product Owner decision in item 119; the recommended behavior is to unwrap it to an empty result and never synthesize text from `w:instr`.
92. `MonoReport.UI/src/components/DocxPreview.tsx` will await normalization before calling `renderAsync`. Each effect invocation continues to own a distinct detached render host and a current-operation flag. If cleanup or source replacement occurs while ZIP/XML work or rendering is pending, the obsolete operation must not call `renderAsync`, publish a warning, or repaint the connected host. Cleanup removes only the operation-owned host; no object URL is needed.
93. Keep the identity boundaries explicit. `App.tsx` continues to retain the selected original `File` for `generateDocument`, and `generation.ts` continues to place that exact File in multipart `template`. A successful response retains the exact original API Blob in `GeneratedDocument`; Download continues to create its URL from that Blob. Only `DocxPreview` receives a normalized copy for rendering. No Core, API, CLI, multipart, response, generated OOXML, or downloaded-byte change is proposed.
