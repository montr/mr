# Feature 004 — MonoReport.UI Implementation Plan

## 1. Status and Planning Basis

1. The Product Owner approved the complete Feature Spec on 2026-10-13. This Developer plan is awaiting independent Reviewer assessment and separate Product Owner approval. Implementation is not authorized by specification approval or by preparation of this plan.
2. This plan is based on the approved `feature-spec.md`, approved `monoreport-ui-mockup-v10.html`, `AGENTS.md`, the Feature Developer Skill, the current repository and uncommitted state, Feature 003's implemented endpoint and Problem Details code, Feature 003's HTTP/OpenAPI/host tests and recorded evidence, the root README, and the existing sample DOCX and JSON files.
3. The implemented generation contract is `POST /api/documents/generate` with multipart file part `template`, text part `data`, and optional text part `culture`. Feature 004 will omit `culture`. Success is raw bytes with the DOCX media type and attachment filename `document.docx`; application failures are RFC Problem Details with `type`, `title`, `status`, `detail`, `code`, `traceId`, and nullable `field`.
4. The approved mockup controls layout and interaction intent, but its simulated document markup, five hardcoded diagnostics, fake result construction, and alert-only download are reference-only and will not be copied into production behavior.

## 2. Dependency and Project Choices

5. Add a standalone `MonoReport.UI` npm project using React and TypeScript, Ant Design for accessible controls and busy/error presentation, Webpack for development and production bundles, and SWC through `swc-loader` for transpilation. Run `tsc --noEmit` separately because SWC does not type-check.
6. Use `monaco-editor` directly with its Webpack plugin and JSON language contribution. Do not add another editor wrapper unless implementation proves that direct lifecycle integration cannot meet React cleanup and test isolation requirements; that would be reported as a plan deviation before adoption.
7. Use `docx-preview` directly for template and result rendering. Keep each preview render bound to an operation token and owned container, clear obsolete content, and release owned object URLs or other browser resources on replacement and unmount.
8. Use Vitest with jsdom, React Testing Library, `@testing-library/user-event`, and `@testing-library/jest-dom`. Use Vitest's own mocks and assertions; do not add Jest, Playwright, snapshots, pixel comparisons, or coverage tooling.
9. Pin direct dependency versions in `package.json`. Generate and retain the npm-generated package-lock.json as part of the implementation deliverables. Do not stage or commit it. During implementation, resolve mutually compatible current stable releases from the npm registry and record the selected versions in review evidence. Do not use floating dependency ranges in the lockfile or introduce a monorepo/package-workspace manager for this single frontend.
10. Configure `webpack-dev-server` to serve the UI locally and proxy relative `/api` requests to the documented local API origin, defaulting to `http://127.0.0.1:5080`; preserve `/docs/` as a relative production link. The production command emits static assets only under `MonoReport.UI/dist`, which must be ignored and must not be hosted or copied by the API in this feature.
11. Keep UI product metadata in one frontend configuration source. Use package metadata for version `0.0.1` and derive the visible release label and URL from it at build time rather than duplicating the version across components. Preserve the approved repository URL and treat it only as displayed metadata.

## 3. Ordered Implementation Steps

12. Add `MonoReport.UI/package.json`, `package-lock.json`, TypeScript configuration, SWC configuration, Webpack development/production configuration, Vitest setup/configuration, HTML entry template, and project-local ignore rules where needed. Expose exactly the required `npm run test`, `npm run typecheck`, and `npm run build` commands plus a concise development command. Do not add generated `dist` assets to source control or add the npm project to the .NET solution.
13. Establish a small source structure with an application shell, typed state and operation functions, an HTTP generation client, a Problem Details normalizer, Monaco editor adapter, DOCX preview adapter, accessible splitter, focused presentational components, and the approved responsive styles. Keep transport, preview lifecycle, and view state independently testable without a state-management framework or speculative format abstraction.
14. Build the approved shell and styles: compact brand bar; left template toolbar and JSON work area; right Template, Result, and Errors tabs; contextual Download; footer links; neutral light styling; balanced desktop panes; stacked narrow layout; sensible pane minimums; and no mock diagnostics, fake paper content, marketing text, zoom controls, or new logo work.
15. Implement the desktop vertical and narrow-layout horizontal separator as one reusable instance component. Support pointer capture, clamped dimensions, responsive orientation, Arrow key adjustment, `role=separator`, orientation and value attributes, visible keyboard focus, and resize cleanup. Preserve the mockup's 850-pixel layout transition unless browser inspection exposes an accessibility or minimum-size defect.
16. Integrate Monaco as one controlled JSON document initialized to `{}` with JSON syntax highlighting and diagnostics. Preserve editor content across template changes. Implement Copy against the exact current text and Format through JSON parse/stringify so invalid input remains untouched while its syntax diagnostic is also represented in Errors. Keep Form visible and disabled.
17. Implement one shared template-selection path for the file picker and preview-area drag-and-drop. Accept one `.docx` file, reject unsupported files with a clear diagnostic without replacing an existing valid template or result, allow clearing, switch accepted selections to Template, clear prior generation errors and result, and retain JSON. Protect asynchronous preview completion with an operation token so an obsolete selection cannot repaint the current preview.
18. Wrap `docx-preview` rendering for actual uploaded template bytes and successful API result bytes. Render into dedicated containers, show concise independent preview warnings, and distinguish preview failure from generation state. A template render failure does not block Generate; a result render failure leaves Result available and Download enabled for the successful API bytes.
19. Implement result invalidation as a single state transition used by accepted template selection, template clearing, and every JSON edit. The same transition runs before generation and remains in effect after failure. It disposes old result resources, disables Result and Download, and never creates a previous-result state. Only a subsequent successful response restores them.
20. Implement an injected generation client using relative `/api/documents/generate`. Build fresh `FormData` containing the selected `File` under `template` and the exact editor text under `data`; do not set the multipart `Content-Type` header manually and do not send `culture`. Disable duplicate submission and expose an unobtrusive pending state until the one request settles.
21. Validate template presence and JSON syntax only when Generate is pressed. A blocking client error opens Errors and makes no request. A valid request accepts only HTTP success with the expected DOCX media type and a nonempty Blob; it parses a safe filename from `Content-Disposition`, falling back to `document.docx`, stores the actual bytes in memory, opens Result, renders them, and enables a browser download of those identical bytes.
22. Normalize error responses without interpreting unsafe HTML. Prefer recognized RFC Problem Details fields, retain multiple validation-style issues when an `errors` collection is supplied, and otherwise produce one concise transport or unexpected-response diagnostic. Never synthesize Core issues, reveal response markup as HTML, or ship mock errors. Open Errors automatically, display the actual count, use the full preview width, and keep long details scrollable.
23. Make asynchronous state race-safe. Associate each request and preview with the template/JSON revision that launched it, ignore stale completions after input changes, prevent duplicate generation while pending, and abort fetch on unmount or when practical after a superseding operation. An obsolete success must never restore stale Result or Download.
24. Add focused component/integration tests using real `File`, `Blob`, and `FormData` objects where jsdom supports them, with narrow mocks only at browser boundaries such as Monaco, `docx-preview`, clipboard, object URLs, downloads, and fetch. Assert user-visible behavior and captured request bodies rather than Ant Design or third-party internal behavior.
25. Update the root `.gitignore` to exclude `MonoReport.UI/node_modules`, `MonoReport.UI/dist`, and frontend transient caches without masking source, lockfile, or test fixtures. Update the root README to list `MonoReport.UI`, state prerequisites and exact install/dev/test/typecheck/build commands, describe starting the API with the UI development proxy, and state that the production output is static and is not API-hosted or Docker-packaged in Feature 004.
26. Run focused frontend checks while implementing, then the required final frontend test, type-check, and production build. Because no backend behavior is planned to change, reuse Feature 003's existing API malformed-JSON and contract evidence rather than rerunning the full .NET suite. If any backend or shared contract file is unexpectedly touched, stop and escalate the deviation before running the relevant affected API regression tests.
27. Run the API and UI development servers for manual verification with `Samples/sample.template.docx` and `Samples/sample.json`. Exercise actual template preview, HTTP generation, result preview, download, and opening the downloaded DOCX. Use syntactically valid incompatible data such as `{"Materials":{}}` with the sample template to produce the real live HTTP `422`; malformed JSON remains a client-only check with no request.
28. Manually inspect the approved desktop and narrow layouts, pointer and keyboard splitter behavior, keyboard focus, tabs/actions, file picker and drag-and-drop parity, second-template replacement, independent preview failures, unavailable API handling, links, and configured version. Record exact interactions, browser/host details, downloaded artifact validation, limitations, and whether evidence was live, stubbed, or reused in `review.md` during implementation.
29. Inspect the final scoped diff and run `git diff --check`. Submit implementation and verification evidence to the Orchestrator for independent implementation review. Do not stage, commit, push, tag, publish, or treat completed checks as Product Owner acceptance.

## 7. Risks, Constraints, and Deviation Policy

54. Monaco and docx-preview are browser-heavy and jsdom cannot validate their visual rendering. Keep adapters narrow, automate application-owned lifecycle and state, and require actual-browser verification for rendering, focus, layout, and downloads.
55. Preview operations and HTTP requests can settle after template or JSON replacement. Revision tokens, cleanup, and stale-completion tests are required so obsolete work cannot repaint the UI or restore invalidated results.
56. Ant Design and Monaco can materially increase bundle size. This developer playground has no approved bundle-size target; use direct imports and production mode, record resulting artifact sizes, and do not introduce a different component/editor stack without PO-approved scope change.
57. `Content-Disposition` parsing and browser downloads vary by platform. Accept only a safe terminal filename, remove path/control characters, fall back to `document.docx`, and verify both header and fallback behavior automatically plus one real browser download manually.
58. API Problem Details are singular today, while the specification also requires defensive support for validation-style collections. Normalize known safe shapes without inventing new server behavior; malformed or HTML responses become concise generic diagnostics rather than raw content.
59. The repository currently has no authoritative shared product-version source. Frontend package metadata will be the single Feature 004 source for the provisional `0.0.1` footer label and release URL. Introducing a cross-.NET/npm version pipeline would be outside this feature.
60. The existing sample template contains a `Materials` collection, so `{"Materials":{}}` is a concrete syntactically valid incompatibility expected to exercise `generation.invalid_data` and HTTP `422`. Confirm the actual live response rather than hardcoding it in UI tests or production code.
61. No deviations from the approved specification are proposed. If dependency compatibility, browser security, or actual API behavior requires a material change to technology, scope, contract, acceptance evidence, or workflow, stop and route the decision through the Orchestrator and Product Owner before implementation proceeds.
