## 2. Ordered Implementation Steps

4. After reviewed-plan approval, record a baseline Release build and full existing Core/CLI test run before changes. Preserve existing uncommitted work. Use the existing test project for new Core and HTTP tests, adding a project reference to the new API and Microsoft.AspNetCore.Mvc.Testing compatible with .NET 10.
5. Add failing Core tests and public Models/TemplateValidationIssue.cs and Models/TemplateValidationResult.cs. Define stable string codes, safe messages, nullable field/part/location context, immutable issues and read-only snapshot collections; compute Valid exclusively from an empty errors collection. The validator accepts caller-owned readable streams, including non-seekable streams and current-position reads; null/unreadable inputs remain argument errors.
6. Introduce coded TemplateException context through an additive optional constructor parameter/property so existing calls remain compatible. Assign structural codes directly in FieldCodeParser, OoxmlFieldParser and RegionParser at the detecting rule. Assign generation.invalid_data, generation.invalid_format and generation.unknown_formatter at the corresponding resolver, collection rendering, scalar formatting and formatter lookup sites. FormatterRegistry currently throws plain FormatException for unavailable names; introduce typed internal failure information while preserving FormatException compatibility and carry its code through ValueFormatter wrapping. Preserve exception type, existing contextual properties and useful CLI messages. Separate codes from safe HTTP messages and never inspect exception-message text to classify failures.
7. Extract DOCX story discovery and safe XML loading from MergeEngine into injected DOCX-specific collaborators, provisionally DocxStoryReader and TemplateStructureValidator. Enumerate main document first, headers and footers sorted by ordinal package URI within each group, then footnotes and endnotes. Validate main/body and supported story roots. Preserve DTD prohibition. Recognized package-content exceptions are converted only at package open/discovery boundaries; XmlException at part loading becomes template.invalid_xml. Stream-read failures and other unexpected operational exceptions escape. Test package-corruption and injected I/O failures distinctly rather than catch all IOException/InvalidOperationException/ArgumentException as template defects.
8. Implement Services/TemplateValidator.cs using those collaborators and owned buffering/package resources. Collect failures from independently readable parts. Keep shared parsed-field and region information per operation, outside reusable service state. Do not inject data resolvers, formatters or MergeEngine into the standalone validator.
9. Refactor shared structural stages to collect multiple independently detectable failures only when trustworthy state permits: validate complex-field balance and parse field instructions; check nested cached-result fields; pair regions; evaluate individual boundaries and independent-region overlap. Abort dependent checks for an affected story after unsafe field-stack or ambiguous marker pairing failures. For trustworthy parsed fields, collect independent nested-field, boundary and overlap errors in document order. A failed field parse may stop that story's dependent stages. Deduplicate by rule, part and offending anchor, retaining distinct defects. Explicitly document that fail-fast unsafe stages can produce only one issue; no guessed token recovery is added.
10. Route DocumentRenderer.Preflight and MergeEngine through the same structural rules, operating on already-loaded stories. Generation throws the first deterministic structural TemplateException before rendering; it does not call the public stream validator or reopen/traverse the package twice. Preserve public Preflight behavior, rendering behavior, caller stream ownership and independent output bytes. Adapt constructor-composition sites and test fixtures to supply new dependencies externally. Register new services through TryAddTransient in AddMonoReport and test overrides and repeated registration.
11. Add MonoReport.Api/MonoReport.Api.csproj as a separate .NET 10 ASP.NET Core executable and add it to MonoReport.slnx. Reference Core only. Add Microsoft.AspNetCore.OpenApi compatible with .NET 10 and Scalar.AspNetCore; select current compatible stable versions from official package documentation during implementation and record actual versions/evidence. Core and CLI retain their existing non-HTTP dependency boundary.
12. Implement a composition-root Program and injected instance HTTP request/endpoint adapters, provisionally DocumentEndpoints, MultipartRequestReader and ApiProblemFactory. Use primary constructors with null validation, per-request local data, and AddMonoReport. Map the two approved POST routes with explicit multipart metadata. Parse forms once so duplicate text/file representations, missing boundaries and validation extra inputs can be classified consistently. Handle multipart endpoints' automatic antiforgery behavior explicitly for these unauthenticated machine-facing routes; do not add an authentication scheme or hidden token requirement.
13. Implement generation: validate template/data/culture shapes; ignore unknown generation fields; parse one JSON value once with runtime default depth; select invariant culture for omitted/blank culture and GetCultureInfo for an explicit culture; ignore Accept-Language and ambient culture. Dispose owned template stream/JsonDocument. Return raw bytes with DOCX MIME type and safe deterministic attachment filename. Emit warning count only for nonzero engine warnings. Default missing-value policy remains unchanged; exercise the warning-header branch through a controlled test service seam if default behavior yields no warnings.
14. Implement validation: accept exactly one nonempty file named template and reject every additional input. Invoke TemplateValidator directly; return JSON with valid/errors/warnings and all nullable issue context properties. Invalid nonempty DOCX content is a completed 200 validation result. Ensure request shape errors are detected before content validation.
15. Implement the full status/code matrix in Section 3 below using ProblemDetails with type/title/status/safe detail/code/traceId. Use a central safe-message mapping and normalize framework handling when execution reaches the application. Unexpected server failures are sanitized 500 responses, including after a previous failed request; never return partial DOCX output.
16. Configure one positive whole-request size setting with a 50 MiB default, applied to both routes using standard Kestrel/request-size and form options. Align form value and multipart buffering defaults with the overall setting without independent product limits or removing ordinary parser safeguards. Check Content-Length when available and ensure real-host body enforcement for streamed requests. Retain framework ownership of buffering resources. Add no generation timeout, admission queue, concurrency limiter, output limit or 429 mapping. Cancellation applies to asynchronous input/output without promising interruption of synchronous work.
17. Generate OpenAPI for both endpoints, including exact multipart schemas, request requirements, nullable issue context, ProblemDetails machine codes, JSON/binary responses and conditional warning header. Use supported schema/operation transformations only as needed. Configure /openapi/v1.json and /docs as enabled by default in every environment, with `MonoReport:DocumentationEnabled` as an explicit enable/disable override. Start with Minimal APIs and Scalar. Adopt Controllers or Swagger UI only under the approved fallback conditions and record the demonstrated reason; escalate any broader contract change.
18. Add README documentation for both projects/contracts, run commands, request-limit configuration, documentation enabled by default in every environment and its explicit override, complete status/code taxonomy, diagnostic ordering/collection limitations, Core stream ownership and validation independence, invariant culture, public deployment protections, and concise copyable generation/validation HTTP examples. Include CLI --validate examples, JSON diagnostics and exit handling following Section 9 below. The Feature Spec explicitly requests usage examples; do not add unrelated code-formatting examples. Preserve existing Core/CLI generation explanations.
19. Run the targeted and full checks in Section 5, perform and record actual browser workflows, and submit code plus verification evidence for independent implementation review. Orchestrator transitions phases; feature completion still requires Product Owner acceptance.

## 3. Error Contract and Test Matrix

20. Both endpoints: missing, empty, duplicate and incorrectly represented known inputs map to 400 with request.missing_input, request.empty_input, request.duplicate_input and request.invalid_input. Parameterized actual multipart HTTP cases cover applicable template/data/culture text-versus-file combinations and safe ProblemDetails properties.
21. Both endpoints: broken multipart syntax/missing boundary maps to 400 request.invalid_multipart; wrong overall MIME type maps to 415 request.unsupported_media_type. Validation additional data, culture and unknown inputs map to 400 request.unexpected_input. Generation unknown inputs are ignored.
22. Both endpoints: actual body exceeds configured whole-request limit maps to 413 request.too_large when application normalization is possible. Exercise a small test configuration, bodies around the boundary, chunked input and an actual Kestrel host; separately record host-owned rejection before application execution. No 429 status is implemented/documented.
23. Generation: malformed, trailing-content and excessive-depth JSON map to 400 data.invalid_json; invalid culture maps to 400 culture.invalid. Include omitted/empty/whitespace culture, explicit en-GB and a decimal-comma culture, ignored Accept-Language and altered ambient culture.
24. Generation: invalid bytes/package, missing supported main/body structure and malformed story XML map to 422 template.invalid_package, template.unsupported_structure and template.invalid_xml. Validation returns these codes in 200 invalid results. Cover all supported story kinds, independently unreadable parts and inability to discover a corrupted package.
25. Structural codes template.invalid_field_syntax, template.invalid_field_structure, template.invalid_region, template.overlapping_regions and template.unsupported_nested_field each have Core and validation HTTP fixtures. Representative generation fixtures assert 422 with the identical rule code; compare both entry points' structural acceptance and rejection. Check code stability when safe-message wording changes without relying on messages in production classification.
26. Generation: incompatible scalar objects/arrays and collection-as-scalar values map to 422 generation.invalid_data; numeric/date/custom formatting incompatibilities map to generation.invalid_format; unavailable formatter names map to generation.unknown_formatter. Preserve missing-value empty/warning/error Core behavior and existing formatter tests.
27. Both endpoints: injected operational stream/service failures produce 500 server.internal_error and sanitized ProblemDetails. Assert no raw exception message, stack, file path, raw field code, submitted payload or document bytes. Validation content issues do not become 422; generation has no redundant success property.
