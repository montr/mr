## 2. Source Assessment and Dependency Choice

4. MonoReport/Services/MergeEngine.cs constructs MergeContext inside each Merge call and keeps document trees, output streams, and story lists local. DocumentRenderer, parsers, resolver, CachedResultWriter, and ValueFormatter retain injected collaborators rather than operation state. No runtime lifetime or context refactoring is planned.
5. FormatterRegistry copies its supplied dictionary and supports unsynchronized Register mutations. RubSpellOutFormatter uses local work variables and read-only lookup data. The singleton registry is safe for concurrent reads after setup, not concurrent writes; custom formatters must independently satisfy thread safety and singleton-compatible dependencies.
6. MonoReport.Cli/Program.cs manually constructs the complete graph. CliApplication requires CliOptionsParser and MergeEngine. MonoReport.Tests/Services/Docx.cs independently supports manual composition, optional custom registry injection, valid DOCX creation, story inspection, and Open XML validation. Keep that manual path and existing tests intact.
7. Add Microsoft.Extensions.DependencyInjection.Abstractions version 10.0.12 to MonoReport/MonoReport.csproj and Microsoft.Extensions.DependencyInjection version 10.0.12 to MonoReport.Cli/MonoReport.Cli.csproj and MonoReport.Tests/MonoReport.Tests.csproj. The official package pages consulted during planning list matching 10.0.12 stable releases, so use that verified compatible servicing pair rather than the older 10.0.0 baseline; do not introduce prerelease packages. Official [provider package metadata](https://www.nuget.org/packages/Microsoft.Extensions.DependencyInjection/10.0.12) lists net10.0 assets and requires Abstractions at least 10.0.12; [abstractions metadata](https://www.nuget.org/packages/Microsoft.Extensions.DependencyInjection.Abstractions/10.0.12) confirms availability. Restore, dependency/audit warnings, and runtime compatibility must still be checked during implementation. Escalate a material package problem instead of silently changing architectural scope.
8. Do not add ASP.NET Core, Hosting, Options, a separate integration project, or the concrete provider package to the core library. Keep the existing target frameworks and package references otherwise unchanged.
