# Feature 002 — Dependency Injection Integration

## 1. Document Status and Goal

1. This is a draft for Product Owner discussion. Registration as Feature 002 and preparation of this draft are authorized. The Product Owner selected the core-library placement and subsequently directed transient stateless engine services with a singleton default registry and stateless built-in formatters, superseding the earlier scoped registry/engine selection recorded in item 45. The complete revised specification is not yet approved for implementation.
2. Provide conventional .NET dependency injection registration through `services.AddMonoReport()` for library consumers and the CLI, while preserving existing constructor injection and document behavior.
3. Keep the feature in `discussion`. Specification approval, implementation planning, independent plan review, and explicit plan approval remain separate future gates.

## 2. Existing Implementation and Architectural Evidence

4. The core project targets `net10.0` and currently references `DocumentFormat.OpenXml`; it has no Microsoft dependency injection package dependency (`MonoReport/MonoReport.csproj`).
5. The CLI manually composes the graph in `MonoReport.Cli/Program.cs`. `MonoReport.Tests/Services/Docx.cs`, method `CreateEngine`, independently constructs the same graph and accepts an optional custom `FormatterRegistry`.
6. `MergeEngine` requires `DocumentRenderer`. The renderer requires `DataResolver`, `OoxmlFieldParser`, `RegionParser`, `ValueFormatter`, and `CachedResultWriter`. `OoxmlFieldParser` requires `FieldCodeParser`; `ValueFormatter` requires `FormatterRegistry`.
7. The default registry contains `RubSpellOutFormatter` under its existing `spellOut` name. `FormatterRegistry` requires an `IReadOnlyDictionary<string, IValueFormatter>` and copies its entries into a case-insensitive dictionary. Its public `Register` method remains mutable and unsynchronized (`MonoReport/Services/FormatterRegistry.cs`).
8. Existing custom formatting uses `IValueFormatter`, `FormatterRegistry.Register`, and per-merge `MergeOptions.FieldFormatters`. This is verified by the existing `Supports_custom_formatter_registration` test in `MonoReport.Tests/Services/FormatterTests.cs`; no DI-aware formatter registration API currently exists.
9. Reusable engine collaborators keep their dependencies in fields. Document XML, streams, parser stacks, and `MergeContext` are supplied or created for each operation. The mutable formatter registry is configuration state, not merge operation state. These source observations justify evaluating reuse; they do not establish unrestricted thread safety for custom formatters or concurrent registry mutation.

## 3. Scope

10. Introduce one public `IServiceCollection` extension, `AddMonoReport()`, which supplies the complete currently supported DOCX engine graph and built-in formatter.
11. Update the CLI composition root to use that registration mechanism. Register CLI-only collaborators in the CLI; they must not become core library registrations.
12. Preserve manual constructor composition as a supported alternative. Do not require ASP.NET Core, a web host, or DI use inside engine services.
13. Specify service lifetimes, repeat-registration behavior, null handling, and compatibility with existing registry customization before implementation approval.
14. Document library and CLI usage and verify actual DI composition through automated tests during implementation. Existing manual-composition tests need not all be converted.

## 4. Proposed Public API and Placement

15. Recommend a public static `MonoReportServiceCollectionExtensions` class exposing `AddMonoReport(this IServiceCollection services)`, returning the same `IServiceCollection` instance to permit chaining. Reject a null collection with `ArgumentNullException` before changing descriptors.
16. Place the extension in the existing `MonoReport` assembly with a dependency on `Microsoft.Extensions.DependencyInjection.Abstractions`, as selected by the Product Owner. Recommend the conventional `Microsoft.Extensions.DependencyInjection` namespace. This avoids a new integration project while introducing the registration contract dependency into the library. The package version must be compatible with the existing target framework and verified during approved planning.
17. The CLI and DI integration tests need the concrete `Microsoft.Extensions.DependencyInjection` provider package. The core registration extension must not build or own a provider, resolve services during registration, or require the provider implementation package, ASP.NET Core, Hosting, or Options merely to register services.
18. The requested static extension is a composition bootstrap that adds descriptors. Runtime parsing, resolution, formatting, rendering, and merge services remain injected class instances; no static runtime service logic, hidden default constructors, service locator inside engine services, or global provider is introduced. This is the proposed boundary interpretation of Coding Guidelines item 1, subject to approval of this specification; project rules are unchanged.
19. A separate `MonoReport.DependencyInjection` integration project referencing core and DI abstractions was evaluated. It keeps the existing core dependency list unchanged and allows opt-in integration, at the cost of an additional assembly, project, and eventual packaging surface. The Product Owner selected the existing-library alternative instead.

## 5. Proposed Lifetimes and Registration Behavior

20. Following the revised Product Owner direction, register `MergeEngine`, `DocumentRenderer`, `DataResolver`, `OoxmlFieldParser`, `FieldCodeParser`, `RegionParser`, `ValueFormatter`, and `CachedResultWriter` as transient services. Register the default `FormatterRegistry` and stateless `RubSpellOutFormatter` as singletons. No default service requires scoped state. These lifetimes match the actual dependencies in item 6: transient engine collaborators consume the singleton registry, whose only default service dependency is the singleton built-in formatter. The complete descriptor list remains part of this draft for specification approval.
21. Repeated resolution creates distinct default engines and transient collaborators, while the registry and built-in formatter are shared within one provider, including across its scopes. Different providers receive their own container-created singleton instances. Every merge still creates its own `MergeContext`, XML trees, parser stacks, and output data; do not register `MergeContext`, `MergeOptions`, template streams, JSON documents, or operation data as services. Transient registration does not prevent an engine instance from being reused for successive or concurrent merges under the configured-registry conditions in item 27.
22. Default library consumers may resolve an engine directly from their provider; the default graph does not require an application scope. The CLI creates and disposes its provider at the composition root and resolves its application using `AddMonoReport()`, without manually assembling the core graph. An explicit CLI scope is permissible and required if consumer replacements introduce scoped dependencies, but is not a default engine requirement.
23. Register the built-in formatter as a singleton concrete service. The singleton registry factory obtains that registered formatter through its supplied provider and constructs the name-to-formatter dictionary. The default singleton registry must not capture scoped services or mutable transient dependencies. Do not register a generic shared `IReadOnlyDictionary<string, IValueFormatter>` or infer formatter names from unnamed `IEnumerable<IValueFormatter>` registrations.
24. Recommend `TryAdd` semantics for each default concrete service type: preserve existing consumer registrations, supply missing defaults, and add no duplicate descriptors when `AddMonoReport()` is called repeatedly. Repeated calls must not replace a registry, reset custom formatter configuration, build a provider, instantiate the graph, or alter existing descriptor lifetimes.
25. Preserve the built-in `spellOut` behavior for the default graph. A consumer-supplied registry remains authoritative; registration does not mutate it or silently add missing formatter names. Consumers choosing a complete custom registry remain responsible for including any built-ins they require, as with existing manual composition.
26. Consumer registrations made after `AddMonoReport()` follow ordinary .NET container semantics; this feature does not introduce a competing override mechanism or guarantee deduplication of descriptors added explicitly by consumers. Preserve pre-registered overrides without silently changing their lifetimes. Consumer replacements must form a valid lifetime graph and preserve their own thread-safety and disposal requirements; retaining arbitrary overrides cannot guarantee a safe graph. Replacing the built-in formatter with a scoped dependency while retaining the default singleton registry is unsupported. Enable provider build and scope validation when verifying defaults and supported replacement graphs.
27. Existing custom formatter registration remains available through `FormatterRegistry.Register`: configure the default singleton registry before the first merge and perform no registration or dictionary writes during concurrent reads or merges. Once configured and safely made available to consumers, the registry may be shared by transient or reused engines. Concurrent merges must use independent operation inputs and must not concurrently mutate their streams, options, JSON lifetime, or custom configuration. Formatters stored in the default singleton registry must be thread-safe for concurrent use and have singleton-compatible dependency lifetimes. The registry's existing mutable dictionary does not support concurrent registration and rendering; this feature does not add locking, freezing, or a new configuration API.
28. Scoped services are justified only when the consumer's real state or dependencies require them. To use a custom formatter with scoped dependencies, supply an explicit scoped `FormatterRegistry` registration whose factory obtains the formatter within that same scope, before calling `AddMonoReport()` or by explicitly replacing its default registration. Resolve the transient engine in that scope, configure the scoped registry before use, and dispose the scope appropriately. Do not retain the scoped formatter or registry in the default singleton registry or another singleton. Existing registry constructors, `Register`, and standard consumer DI registrations provide this path; no new MonoReport formatter-registration API is introduced. Provider validation cannot discover an opaque formatter object manually inserted into a registry, so consumers remain responsible for that object's captured dependencies and lifetime.
29. The earlier scoped registry/engine approach is superseded by item 20: default per-scope isolation is no longer promised. An all-singleton graph and an all-transient graph were also evaluated and not selected. All-singleton unnecessarily retains inexpensive stateless engine collaborators; all-transient would make an independently resolved registry differ from the registry in a later engine. The selected transient-engine/singleton-registry design supports inexpensive resolution and shared setup-time configuration without inventing scoped state.

## 6. Extensibility and Exclusions

30. Keep `AddMonoReport()` small enough to evolve through additive APIs. A future `AddMonoReport(options => ...)` overload would offer concise configuration; a builder could support richer formatter and format registration. Neither design is required until an approved feature defines real configuration needs.
31. Do not introduce an options object, options overload, builder, formatter discovery, named DI registrations, registration-time custom formatter API, or a complex configuration framework in this feature. Preserve existing programmatic formatter customization instead.
32. The `AddMonoReport` name is format-neutral; the graph registered by Feature 002 implements DOCX only. Preserve current DOCX-specific parsing and rendering boundaries. Future XLSX registration may be additive or format-specific, but no Excel services, shared format-dispatch contract, identical template syntax, or DOCX engine refactoring is authorized here.
33. Exclude HTTP endpoints, custom formatter concurrency changes, conditions, additional formatters or currencies, changing merge result/error behavior, and unrelated architectural cleanup.
34. Do not modify Feature 001 artifacts or status. Do not add a backlog prerequisite, a new mandatory workflow artifact, or implementation work during discussion.

## 7. Draft Acceptance Criteria

35. A plain .NET consumer can call `AddMonoReport()` and resolve a usable `MergeEngine` using the approved lifetime model, without ASP.NET Core or a host. The core graph contains every dependency listed in items 6, 7, and 20.
36. The extension returns the supplied collection and throws `ArgumentNullException` for null input. Registration performs no template processing, provider construction, or eager service instantiation.
37. Repeating registration leaves the number and meaning of MonoReport default descriptors unchanged. Pre-registered consumer descriptors, including a custom registry, are preserved; partially pre-registered graphs receive missing defaults.
38. Resolution with the default graph preserves existing built-in `spellOut`, scalar fields, collections, re-merge behavior, culture/options handling, and F1–F3 corrections. DI does not change generated DOCX content, field codes, formatting, or diagnostics.
39. Verify the descriptors have exactly the lifetimes in item 20. Repeated resolution produces different default engine and transient collaborator instances; the default registry and built-in formatter are the same within and across scopes of one provider, and separate providers receive separate default singleton instances. Direct root-provider engine resolution succeeds with build and scope validation enabled. No scoped defaults or DI registrations for per-operation models are introduced. A new `MergeContext` is used on every merge, including successive calls on the same engine.
40. A custom formatter added through the existing `Register` API before first use is available to subsequently resolved engines sharing the default registry and works with `MergeOptions.FieldFormatters`. Verify a consumer-supplied scoped registry with a formatter having scoped dependencies is used by engines resolved in that scope, isolates registry state between scopes, and passes provider validation. Verify that attempting to resolve a scoped built-in formatter dependency from the default singleton registry is rejected when scope validation is enabled. No singleton capture is introduced in supported graphs. Existing manual construction and custom registry injection remain valid; replacement registries are not silently mutated or repopulated.
41. Test concurrent merges through independently resolved transient engines sharing a configured default registry, and concurrent merges through one reused engine with that same registry. Use independent streams, data, and distinct per-merge options, and a thread-safe custom formatter where relevant; assert correct values, diagnostics, independent output documents, document structure, and unchanged template input bytes without cross-operation state. Concurrent registry mutation and unrestricted custom formatter thread safety remain outside the contract. These checks must not claim that DI scope validation detects manually captured opaque formatter dependencies.
42. Actual CLI invocation uses the new registrations and preserves successful generation, binary stdout/file output, invalid-template errors, and protection against overwriting outputs on rendering failure. The existing full automated suite and Release build pass; new DI tests cover graph resolution, exact descriptor and instance lifetimes, repeated registration, preserved consumer overrides, safe scoped customization, invalid scoped capture with validation enabled, and concurrent merges. Generated DOCX verification checks Open XML validity and observable content/field formatting independently.
43. Documentation explains dependency installation, root-provider use for the default graph, provider ownership/disposal, setup-before-first-merge registry configuration, thread-safety and captured-lifetime responsibilities, and explicit scope use only for consumer replacements that require it. Future configuration APIs and XLSX integration are not implemented. No unrelated code, test migration, or core refactoring is included.

## 8. Recorded Product Owner Decisions and Remaining Approval

44. Product Owner decision: use the existing MonoReport library with DI abstractions. Do not introduce a separate integration project for this feature.
45. Decision history: the Product Owner initially selected scoped registry/engine lifetimes, then explicitly superseded that choice with transient stateless engine services, a singleton default formatter registry and stateless built-in formatters, and scoped services only where genuine state or dependencies justify them. Keep `MergeContext` per merge, preserve `TryAdd` consumer overrides, require a valid concurrent-use/lifetime graph, and introduce no new custom formatter configuration API. Item 20 and criteria 39–43 reflect the revised direction; the earlier all-scoped recommendation is not operative.
46. Review the proposed namespace, composition-bootstrap boundary, complete graph, `TryAdd` policy, consumer registry authority, and exclusions as part of explicit specification approval. These are recommendations, not silently approved requirements.
47. The architectural answers in items 44–45 do not constitute approval of the complete Feature Spec. Explicit specification approval remains pending; Feature 002 remains in `discussion`, with phase transitions owned by the Orchestrator. No implementation plan or application/test changes are authorized by this document.

## 9. External Technical References

48. Microsoft's [service registration documentation](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/service-registration) describes group registration through an `Add` extension and `TryAdd` behavior. These established conventions support the API and repeat-registration recommendations; they do not decide MonoReport product behavior.
49. Microsoft's [dependency injection guidelines](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/guidelines) distinguish container safety from service thread safety, describe scope ownership, and advise against building providers during registration. The lifetime recommendation additionally relies on the repository's mutable registry observed in item 7.
